# Workflow Review: Settings Form Validation Drill

This workflow drill compared the first and second iterations of the settings form to measure whether the later pass resolved real product issues while preserving the original intent. The concrete code difference was significant. In Round 1, validation logic remained inside `script.js`, which made the rules harder to isolate and test. In Round 2, that logic was extracted into a dedicated `validation.js` module. That change improved maintainability because the validation rules could be reused and tested independently without needing to mount the browser UI first.

From a correctness perspective, Round 2 was more complete. It introduced `displayName` and a `notifications` select, and it explicitly handled empty and whitespace-only display names. It also validated invalid and valid email strings through a reusable function, producing clear messages for each condition. Those changes directly addressed known edge cases that were otherwise easy to miss in a form-only prototype. In practice, the stronger requirement handling made the feature more reliable because invalid data was blocked before submission and the success state only appeared when the inputs were valid.

Accessibility also improved in Round 2. The form used semantic label/input associations with `for` and `id` attributes, and it kept `aria-live="polite"` on validation status messages so users received updates without needing to read the whole page. This is a meaningful improvement over a less structured pattern where validation messages might exist visually but not be announced appropriately. However, one concrete problem in Round 2 was caught during review: the notification help text incorrectly used the `error-message` class and `aria-hidden="true"`. That meant the help note looked like an error and was hidden from assistive technology, even though it was not meant to be an error. This was a real AI mistake and it demonstrated why review must include semantics, not just visual behavior.

The testing and verification story also improved. Round 2 added `validation.test.mjs` and `package.json`, which allowed validation rules to be tested independently from browser UI behavior. That made regression checks easier and more targeted. The tests covered empty, whitespace-only, invalid, and valid inputs. This was a stronger quality-control practice than relying only on manual checks. At the same time, Round 2 still lacked browser automation tests, so there remained a gap between unit validation correctness and end-to-end form interaction in a real browser.

Review and fixing effort was moderate and valuable. The main code cleanup work in Round 2 included separating validation into reusable functions, adding tests, and addressing form semantics. The review also found an unused payload object in `script.js`, which is not a functional bug but is an example of cleanup that should be removed or replaced with a real save step before shipping. The overall maintainability story is better in Round 2 because the validation and tests are decoupled from presentation logic, but there is still room to tighten the final polish by removing dead code and adding browser-level coverage.
